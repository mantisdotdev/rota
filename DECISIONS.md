# Decisions

What was decided, why, and when to look again. One row per decision. IDs are sequential and never reused. `Decision` says what; `Why` gives the reasons and the alternatives rejected, plus the date for rows added after the seed; `Revisit when` names the trigger that reopens it. D-001–D-010 are the seed from PRD §15 (v0.1, September 2026). Append new rows; edit old rows only to record a revisit outcome. A choice the PRD does not cover gets a row here before the code that depends on it (CLAUDE.md, Edit rules). The product was Pattern Box until D-043: rows before it that say Pattern Box, `PB2` or `PB2S` mean Rota, `RT2` and `RT2S`.

| ID | Decision | Why | Revisit when |
|---|---|---|---|
| D-001 | Elastic cycle model, not a step grid. | It's the only thing in the category that makes rhythm feel alive, and it's what makes sharing as text possible. | Never; this is the product. |
| D-002 | Rests via skip button plus kit smart defaults. | Without rests the backbeat is impossible; without smart defaults beginners hit that wall in minute one. | After usability round 1 if testers don't find skip. |
| D-003 | Edits commit on the next beat. | Avoids mid-hit stumbles. Unproven with users. | A/B in usability round 1 against instant commit. |
| D-004 | Hold pad + knob = per-track version of that knob. | One grammar to learn instead of menus. | If testers accidentally edit tracks while trying to mute. |
| D-005 | MCU firmware, not Linux. | Instant on, 20 h battery, sub-$90 BOM. Own engine makes it possible. | If v2 needs sample import or wireless-heavy features. |
| D-006 | No per-step chord editing in v1. | Keeps the melodic pads as simple as the drums. Progression is kit-defined. | If casual producers name it as the top missing feature. |
| D-007 | Jam over TRS MIDI cable, no radio. | Removes radio certification and pairing UX from v1. | v2. |
| D-008 | Own engine and syntax; Strudel-like text view for export only. | Independence, licensing clarity, and syntax designed for the device. | — |
| D-009 | Encoders, not pots. | Values are saved per section and must recall without jumps. | Cost review at DVT. |
| D-010 | One C++17 codebase behind a HAL: Teensy firmware, desktop SDL2 simulator, and later a WebAssembly web player. | No engine port and no drift between web and device; the device is the product, so its code comes first. | If the Emscripten build is too large or slow on phones. |
| D-011 | Swing is encoded in the share code as an integer 0–100 (hundredths); filter, fx and chance stay in tenths. | 2026-09-02. The lofi kit's swing is 0.15 (§6.3, Appendix A) and tenths cannot represent it, so a loop with default swing would reload with a different feel. PB2 has not shipped, so widening the field costs nothing. Rejected: rounding to tenths on encode (silent fidelity loss); changing the kit default to 0.2 (bends the sound to fit the format). | If another field needs finer resolution; then redesign the field encoding as a whole rather than widening one field at a time. |
| D-012 | Per-track level is set by holding a pad and using the volume control (one press or detent = 0.1); volume alone stays master volume. | 2026-09-02. §6.2 and §10.1 defined and encoded track level, but §8.1 gave the four knobs to speed, tone, send and chance, so nothing on the surface could set it. Hold-pad-plus-control is the grammar users already learn (D-004), so no new gesture. Rejected: dropping level from the model (loses per-track mix). | If testers change a track's level while trying to change master volume. |
| D-013 | Steps per track capped at 16 (was 32). A section code under 200 characters is a target for typical loops, not a limit; the 16-step worst case is 230 characters for the lofi kit and fits a byte-mode QR at version 10-L (271 bytes), drawn at 3 px per module on the 240 px screen. Song codes are never shown as a QR. | 2026-09-02. §10.2's 200-character rule and §12's 32-step cap could not both hold (8 × 32 step characters alone is 256), and the QR-version-6 rationale assumed alphanumeric mode, which the code's lowercase letters and punctuation rule out (byte-mode v6-L holds 134). Rejected: keeping 32 steps with a larger QR (unreadable at 240 px); a terser grammar (loses readability). | If testers hit the 16-step cap in normal play. |
| D-014 | Per-track level, tone, send and chance are stored in tenths; one detent while holding a pad changes a value by 0.1; kit defaults for these four must be multiples of 0.1. The lofi chord send is 0.4 (was 0.35). | 2026-09-02. Same class as D-011: the modifier group is written in base36 tenths, so a kit default of 0.35 could survive only while the group was omitted and would reload as 0.3 or 0.4 the moment any chord value changed. Making the storage and the kit contract match the format removes the whole class of bug. Rejected: rounding on encode. | If a kit author needs finer per-track values; then widen the modifier digits under a new version prefix. |
| D-015 | doctest v2.5.3 vendored as a single header at `tests/doctest/doctest.h` with its MIT `LICENSE.txt`; SHA-256 `cfd518a3ef90f67e1f3ba514df23fb3627437de1a2feeba78cf5062a40021421`. | 2026-09-02. Header-only, no package manager or extra build step, fast to compile, and tests run on the host only (§12). Vendoring rather than fetching at configure time keeps the build offline and pinned. Rejected: Catch2 (needs a build or a far larger header), GoogleTest (needs a build), CMake FetchContent (network at configure time). | If tests need fixtures or parametrisation doctest lacks. To update: replace the header and this row's version and hash. |
| D-016 | The SDL HAL lives at `firmware/src/hal/sdl/` beside `hal/teensy/`; `host/` holds only the CMake build and the simulator entry point. PlatformIO excludes `hal/sdl/` with `build_src_filter`; CMake excludes `hal/teensy/` and `firmware/src/main.cpp`. | 2026-09-02. PRD §12 names `hal/sdl/` but not its parent, and CLAUDE.md said "under host/". One `hal/` tree keeps §12 rule 1 (engine and sound include nothing platform-specific) checkable with a single grep. Rejected: `host/hal/sdl/` (splits the HAL across two trees). | If a third platform (Emscripten, §12) makes `firmware/src/hal/` the wrong home for code that never runs on the device. |
| D-017 | CI on GitHub Actions: one job builds the host and runs the tests on Ubuntu (apt `libsdl2-dev`); a second installs PlatformIO with pip, caches `~/.platformio/.cache`, and compiles `teensy41`. Both run the exact commands from CLAUDE.md. | 2026-09-02. A green host build says nothing about the firmware: different compiler, no SDL, no exceptions or RTTI, no heap rules. Both must build on every push. Rejected: a single job (serialises the toolchain download behind the fast host build); no firmware job (lets layer violations in until someone flashes a board). | If CI minutes matter, or a self-hosted runner with the toolchain preinstalled appears. |
| D-018 | Share codes use only `A–Z a–z 0–9 : . , - ~` (plus `;` `/` in songs): tracks are joined by `-` (was `\|`), a sharp root is written with `s` (`cs`, was `c#`), and the lineage suffix starts with `~` (was `#`). The prefix stays `PB2`; this is the last pre-release grammar change. | 2026-09-02. `\|` and `#` are not allowed unencoded in a URL fragment, `#` would end the fragment early, and both break message auto-linking, which the §3 share-to-a-phone metric depends on. Every replacement is one byte, so G-14 stays at 230, and byte-mode QR takes any of these bytes as-is. Rejected: percent-encoding in the QR (longer, unreadable as text); an uppercase alphanumeric-mode grammar (cannot carry the URL's own `#`); bumping to PB3 (no decoder exists yet). | Never for PB2 once a device or player ships; any later change is PB3. |
| D-019 | The web player is one self-contained HTML file: the WebAssembly build and the kits' audio are inlined, no external assets, at most 4 MB. | 2026-09-02. §9.5 said "works offline as a single file" and §10.3 said "single HTML file plus assets"; a page opened from `file://` cannot fetch sibling files in current browsers, so only the single-file reading delivers offline play. Three kits' drum samples plus the wasm fit well inside 4 MB. Rejected: file plus assets (fails offline and `file://`); a service worker (setup, no gain for one file). | If a fourth kit or a bigger wasm pushes the file past 4 MB; then split kits out and accept online-only. |
| D-020 | A melodic step's `note` (0–7) is a position in the kit's chord progression (chord pad) or note sequence (pluck pad). Taps assign positions in order and wrap at the list length; a position past the end plays position mod length and is stored unchanged, so codes round-trip. Drums and bass carry note 0 in every code the device writes (revisited 2026-09-02: a decoder accepts and keeps any position on every track and ignores it there, as PRD §10.1 and share-format §2 say; G-14 carries `v` on the bass and round-trips under `RT2` unchanged, T-15). | 2026-09-02. The engine stores one small integer and the kit owns all pitch knowledge, which is how "no wrong notes" (§8.4) and key changes (T-43) fall out for free; scale degrees would need chord qualities in the engine. The PRD example's chord `023` was unreachable by tapping and is now `0123`. Rejected: scale degrees; rejecting out-of-range positions (would refuse codes from bigger future kits). | If per-step chord editing (D-006) ever ships. |
| D-021 | A chord on scale degree `d` is the mode's degrees `d`, `d+2`, `d+4` (stacked thirds, wrapping into the next octave; quartal stacks in pentatonic modes) and its root is `d`. A progression is 1–8 degrees per mode; lofi defines all five modes. Scale intervals for the five modes are fixed in Appendix B. | 2026-09-02. Kits then hold only degree numbers, every chord note is in the scale by construction, and the bass root is the same number. Rejected: chords as (degree, quality) pairs (more kit data, out-of-scale notes possible in pentatonic modes); fixed voicings per kit (no key changes). | If the quartal pentatonic chords test badly with users; then add an optional quality field. |
| D-022 | Speed 0.5 stretches the step list over two cycles: step `i` of `n` spans `[2i/n, 2(i+1)/n)` of the cycle pair, so an odd count splits unevenly (3 steps: 0 and 2/3 on even cycles, 1/3 on odd). | 2026-09-02. It is the elastic rule of D-001 applied to a two-cycle span, so the engine has no special case; "first half / second half" only described the even case. Rejected: padding odd lists with a rest (changes what the user tapped). | Never; it is D-001 over two cycles. |
| D-023 | Ghost hits may land on rest steps: chance adds a ghost at the midpoint of every step on a drum track, rests included. | 2026-09-02. Rests are the gaps where fills sound musical, which is what chance is for (§2, §6.5); excluding them needs a rule and makes backbeat tracks evolve less. Rejected: hit steps only. | If ghosts on rests make chance sound busy in usability round 1. |
| D-024 | A tap on a full track (16 steps) adds nothing; the audition sound still plays; the status line says `<pad> is full`, e.g. `kick is full`. | 2026-09-02. The cap (D-013) needed a visible outcome, and Appendix D copy says what happened in three lowercase words. Rejected: replacing the last step (destroys work); silent ignore (the tester asks why nothing happened). | If testers hit the cap often (see D-013). |
| D-025 | Song code `PB2S:<A>;<B>;<C>;<D>/<arrangement>[~lineage]`. Each section is a full section body (everything after `PB2:`, no lineage); all four are always written, an empty one as eight empty tracks; all four must name the same kit or the code does not load; the arrangement is 1–64 letters A–D with no separators, each letter playing that section for one cycle. | 2026-09-02. One decoder for both code kinds, no special empty form, and the kit is a device setting (§9.4), so one kit per song is the only state the device can hold. 64 cycles is 2.5 minutes at 100 bpm. The §6.8 example `AABA BBCD` had a meaningless space and is now `AABABBCD`. Rejected: a song-level kit field (a second section grammar); spaces as bar groups (no meaning, not URL-safe). | If users want a letter to mean more than one cycle; then add a repeat digit (`A4`) under PB3. |
| D-026 | Loading a code whose kit the device or player lacks: load it with the current kit, say so in the status line (`no kit jazz, using lofi`), apply the current kit's defaults to omitted modifier groups, and encode the current kit's id from then on. | 2026-09-02. §3 goal 3 says a code loads on any device; refusing would fail it for every community kit. The substitute kit's defaults are the only defaults the device knows. Rejected: refusing to load; keeping the foreign kit id in state (would encode a kit the loop no longer plays with). | If kits become downloadable on the device; then offer to fetch instead. |
| D-027 | The lofi kit is fully specified in Appendix A: sample file and settings per drum pad, synth preset and octave per melodic pad, sends, no choke groups, smart-default templates (§6.6), chord progressions for all five modes, the pluck sequence, three dice starting loops, swing 0.15, filter 1.0 and fx 0.2 defaults, sidechain 5 dB / 120 ms. §12 rule 6 lists the same fields. | 2026-09-02. A kit file could not be written from the old one-line appendix without guessing progressions for four modes, the pluck notes, octaves, dice loops or the sidechain depth. Values follow §12's ranges (sidechain 4–6 dB → 5). | When the first recorded samples change what sounds right. |
| D-028 | Dice data is kit data: a kit defines 1–4 starting loops as share codes (only their tracks are used). Dice press picks one with the seeded PRNG and fills the empty tracks from it; dice hold clears every track and fills all eight from a fresh pick (with undo). | 2026-09-02. §8.2 said "re-rolls", which needs more than one loop to roll among, and the seeded PRNG already exists for chance, so tests stay deterministic. Rejected: generating loops procedurally (a second pattern generator to test); one fixed loop (nothing to re-roll). | If three loops feel repetitive; raise the cap. |
| D-029 | CI greps `firmware/src/engine` and `firmware/src/sound` for platform includes (Arduino, SDL, `hal/`, Teensy core headers) and fails on any hit, before either build runs. | 2026-09-02. §12 rule 1 is the line that keeps the engine portable; a grep is the cheapest possible enforcement and catches a violation the firmware build would happily compile. Rejected: a CMake-level include check (host only); waiting for a violation. | If the denylist misses a header; extend it rather than removing the step. |
| D-030 | Song mode with no new controls. `show` cycles ring → text → song view (one screen). In the song view, A–D presses add one cycle of that section to the arrangement (undo removes the last letter, 60 levels; hold dice clears), the pads are eight always-saved songs (tap to switch; an empty song becomes a copy of the current one), and play plays the song from the top. From any view, hold a section button + press play plays the song; play stops it; a section press during song play returns to live mode at that section. Songs on the device: 8 (was 16), one per pad. | 2026-09-02. Tap-to-add is the product's own grammar (D-001) applied to sections, so there is nothing new to learn; the song view is one screen behind the button that already means "show me"; the pads mirror the eight tiles on screen, so every song has a physical place; auto-save with copy-on-empty is the section rule (§6.8) one level up, so nothing can be lost or forgotten. Rejected: record-as-you-play (needs a timed performance, is invisible until done, and collides with tap tempo on play's hold); 16 songs via a bank or a knob-scrolled list (one more concept and no 1:1 physical mapping; 8 songs × 4 sections is already 32 loops); an explicit save gesture (a thing to forget and a way to lose work). | If testers want more than eight songs, tap a pad in the song view expecting a sound (watch item in `spec/scenarios.md`; fallback: hold a pad to switch songs), or want a letter to mean more than one cycle (see D-025). |
| D-031 | Text-view chord names are the root plus `m` when the chord is a minor triad (minor third and fifth above the root); every other chord, including the quartal chords of the pentatonic modes, shows the root alone. | 2026-09-02, user ruling. Naming beyond major and minor needs a scheme the target users (§5) do not read; the root alone is short and never wrong. Rejected: `sus` or quartal suffixes. | If the live-coder community asks for full names in the export. |
| D-032 | The text view spells pitches by the key signature of the current key: seven-note modes use each letter name once; pentatonic modes are spelled like their parent (natural minor or major); dorian takes the signature of the major key a whole tone below its root; when the root has two names (`cs` is C# or Db) the spelling with fewer accidentals wins and a tie goes to flats. Pluck notes use the same spelling, lowercase with the octave of scientific pitch notation, which belongs to the letter: MIDI 83 spelled Cb is `cb6` (revisited 2026-09-02, user ruling; was "the MIDI octave", which would print `cb5`). Codes are unchanged: roots stay in sharps (`s`). | 2026-09-02. Conventional notation is what the tertiary user (§5) reads and what the §9.2 example already shows (`Ab Eb Bb` in C minor); one computable rule covers chord roots and pluck notes with no table to maintain. Rejected: always sharps (misspells every flat key, `A#` in C minor); a per-kit or per-key spelling table (data for a rule that can be computed); ties to sharps (D# minor is rarer than Eb minor). | If the tie-break (Gb major, Eb minor, Ab dorian) reads wrong to testers; flip it to sharps. |
| D-033 | Smart-default template progress is read from the track's steps, never from a counter: an empty track takes the pad's first template; a track equal to template k takes template k + 1; anything else appends a plain hit (its position by D-036). | 2026-09-02. §6.6 counts taps, but a counter cannot travel in a share code and misfires after edits: a loaded `~ sd ~ sd` would shrink to `~ sd` on the next tap. Read from the steps, templates are a pure function of the pattern, so undo restores them for free (T-13) and a loaded `~ sd` grows to `~ sd ~ sd`. Rejected: a per-track tap counter (hidden state that no code carries). | If testers expect a later snare tap to keep doubling instead of appending. |
| D-034 | `events()` draws chance and humanize from a stream fixed by (session seed, cycle index): the same cycle always rolls the same dice, however often and in whatever order it is asked. Every hit draws its numbers whether or not chance can act on it. Dice picks take one value from the app's PRNG as `roll`; the loop is `roll mod count`. | 2026-09-02. The scheduler will ask for the current cycle again when an edit commits mid-cycle (§6.7); a generator advanced across calls would re-roll the beats not yet played. Drawing unconditionally makes chance 0 restore the authored velocities exactly, not just the times (T-10, §6.5). Rejected: one PRNG object shared across calls (order-dependent); rolling the dice loop inside the engine (the app owns the one PRNG a session has). | If replaying a cycle in song mode makes chance sound repetitive; then mix the arrangement position into the stream. |
| D-035 | Undo and redo restore the pattern (steps, hits, notes, alternation, speed) and carry the performance parameters across unchanged: bpm, filter, fx, chance, swing, key, per-track level, tone, send and chance, and mute. | 2026-09-02. T-13 wants the exact previous pattern; encoders must recall "without jumps" (D-009), and undoing a tap must not move a knob the player turned in between. Rejected: snapshotting everything (knobs jump on undo); a second undo stack for knobs (§6.5 calls chance a performance control, not an edit). | If testers try to undo a knob turn. |
| D-036 | A new melodic step's position is the last hit's position + 1, wrapping at the kit's list length; a track with no hit starts at 0. | 2026-09-02. §8.4 says taps "assign positions in order"; continuing from the last hit keeps the progression going after a loaded code (a loaded `5` on lofi is followed by 2, the next chord), where counting hits would repeat the chord just played. Every tapped example (T-41, T-44) comes out the same either way. Rejected: position = number of hits so far. | If per-step chord editing (D-006) ships. |
| D-037 | The bass reads the chord step whose span holds its unswung time, at the chord track's own speed; on a rest it takes the last chord hit before it, wrapping round the cycle; with no chord hit at all it plays the key root. | 2026-09-02. §6.4 says "whichever chord step is active", but a rest holds no chord; the last chord is the one still ringing, which is what a bass line follows. Rejected: the key root on every rest (the bass leaves the harmony on `Cm ~ Ab ~`). | If following the last chord sounds wrong against chords that stop. |
| D-038 | Undoable edits: tap, remove last step, split, skip, swap, speed, dice press and hold, and loading a code. Everything else changes the live state directly: global knobs, key, per-track level, tone, send and chance, mute. A call that changes nothing (a tap on a full track, a split with no hit to split, a speed already at its limit) records no undo level. | 2026-09-02. §6.7 lists the pattern edits and §6.5 calls chance a performance control; the per-track values are the same knobs applied to one pad (D-004). Recording no-ops would spend undo levels on nothing (T-34). | With D-035. |
| D-039 | The decoder refuses anything outside the grammar (a value out of range, an unknown alt, speed or step character, more than 16 steps, not exactly 8 tracks, a malformed lineage), so the status line can say `that code did not load`. It accepts leading zeros in integers and re-encodes them canonically, and it skips extra `:` fields and characters after the four modifier digits (T-16). | 2026-09-02. Validate at the boundary (CLAUDE.md); a partly loaded loop would play something its sender never made. Leading zeros cost nothing to accept, and only canonical codes are promised a byte-identical round trip (share-format §4). Rejected: truncating long tracks; clamping out-of-range values. | If a PB2 code in the wild fails for a reason this list should tolerate. |
| D-040 | Engine time is an exact rational (`Fraction`: int32 numerator and denominator), never a float. | 2026-09-02. 1/3 must be the same 1/3 on the host, on the device and in a test (§12 rule 5: the simulator is the reference behaviour), and a test can then say `Fraction{1, 3}` the way the scenario table does. Denominators stay under 10 000 (16 steps × 4 hits × 2 for speed, and 2 400 for swing). Rejected: double (platform rounding, approximate assertions); fixed-point ticks (no tick count divides 3, 5 and 7). | If the scheduler needs something a rational cannot give (it does not). |
| D-041 | Events carry MIDI pitches resolved by the engine: `note` is the bass root, the pluck note or the chord root (0 on drums), and a chord event adds the two upper tones in `chord_upper`. | 2026-09-02. Sound needs pitches, not positions, and §6.4 resolves the bass "at event time", which needs the key and progression only the engine holds; a chord is always three tones (D-021), so a fixed pair covers it. Rejected: events carrying progression positions (sound would need the key and kit data); a variable-length note list per event (nothing needs it). | If a kit wants four-note chords; then widen the pair. |
| D-042 | Split on an empty track or on a trailing rest changes nothing; skip appends a rest even to an empty track. | 2026-09-02. §8.2 says split cycles "the last step's hits" and a rest has none; the app answers with `add a hit first` (T-07). A lone rest is a legal silent one-step track, and refusing it would need a rule nobody asked for. Rejected: turning the rest into a hit. | If testers press split on a rest expecting a fill. |
| D-043 | The product is Rota (was Pattern Box). Share-code prefixes are `RT2` for a section and `RT2S` for a song (were `PB2`, `PB2S`); the grammar behind them is unchanged. This supersedes D-018: D-043 is the last pre-release change to the format. | 2026-09-02, user ruling. The name changed before any device, player or code shipped, and a prefix spelling the old name would puzzle every future reader of a code. The new prefixes are the same length, so every golden code keeps its length and G-14 stays 230; no decoder has shipped, so the change costs nothing now and would cost a version bump later. Rejected: keeping `PB2` under the new name (misleading forever); bumping to `RT3` (nothing for it to be distinguished from). | Never for `RT2` or `RT2S` once a device or player ships; any later change is `RT3` for sections and `RT3S` for songs. |
| D-044 | The repository is public under a plain all-rights-reserved notice (`LICENSE`: "Copyright (c) 2026 [mantisdotdev]. All rights reserved.") until the crowdfunding campaign; the open-source licence is chosen then. | 2026-09-02, user ruling. The kit format is meant to be open after v1 (§12 rule 6) and the live-coder community matters (§5), but a licence picked before the campaign fixes terms the campaign may need to set differently for firmware, kits and hardware files. A plain notice keeps every option open while the code is public for review. Rejected: MIT or GPL now (hard to take back); a private repo (the web player and community kits need the code in the open). | At campaign time (PRD §14, phase 5). |
| D-045 | The EVT's 11 buttons (7 round, 4 section) are the spare keys of a second NeoTrellis 4×4 at I2C address 0x2F (jumper A0), on the same bus and driver class as the pads; round-versus-square shapes and the ~16 mm pad size wait for the custom keypad at DVT. | 2026-09-02. Four shared wires and one library class against fifteen switch and LED lines with resistors; every key is backlit in RGB for free, so the stateful buttons (§7.2) cost nothing extra; both boards and keypads are in stock at Adafruit and DigiKey India. Rejected: 12 mm tactile switches with coloured caps (opaque caps, a plastic click instead of silicone, hand wiring); illuminated pushbuttons (red-only LEDs, or 29 mm deep in a 20 mm device). | DVT, when the custom silicone keypad (Table 2) replaces both boards. |
| D-046 | The three pad suppliers for the §16 blind feel test are the Adafruit 1611 keypad on the NeoTrellis, the SparkFun 4×4 button pad (COM-07835) on its breakout PCB, and factory samples from Xiamen Better Silicone: S188 (100 mm pad, 15 mm keys, 8.7 mm dome) and S619 (the Adafruit geometry). | 2026-09-02. The SparkFun pad is the only distributor-stocked 4×4 with a verified different geometry and a stated force; Better Silicone draws both a low dome and the Adafruit outline, so the test can separate key shape from compound. Rejected: Adafruit Trellis 1616 (same keypad by Adafruit's own description) and Pimoroni PIM551 (keypad origin unpublished). | After usability round 1 (§14 phase 2). |
| D-047 | The EVT display is the QDtech MSP2834 2.8" IPS module (Elecrow DLS29028B, ILI9341V, 4-wire SPI) driven by vindar/ILI9341_T4 on SPI1; a domestic TN module of the same pinout family is ordered as the bring-up stand-in; the Displaytech DT028DTFT-IPS-SHB panel is the production-direction candidate. | 2026-09-02. It is the only 2.8" 320 × 240 module whose own specification says IPS, with a controller the one Teensy 4.1 driver that does differential DMA redraws and vsync supports, which is what a 60 fps ring on a 10 MHz-rated controller needs; Adafruit sells no 2.8" IPS at all. Elecrow's delivery to India is unverified, so the INR 799 TN module keeps firmware moving. Rejected: Adafruit 1770 (TN, 6 o'clock viewing); Waveshare HX8347D (IPS but no Teensy DMA library); the Displaytech bare panel for the breadboard (15-pin FPC and a 6 V backlight driver). | When the IPS module arrives; if it takes more than three weeks, build the Displaytech adapter early. Again at DVT panel selection. |
| D-048 | EVT PSRAM is the Espressif ESP-PSRAM64H, bought as the unbranded Adafruit 4677 from DigiKey India, not the AP Memory APS6404L-3SQR-SN that SparkFun sells. | 2026-09-02. PJRC tested both on the Teensy 4.1 pads and reports the same silicon; 4,649 in stock in India against a parcel from the USA. The 1.8 V ESP-PSRAM64 (no H) must never be substituted. | Production (Table 2 names the AP Memory part with a second source). |
| D-049 | The EVT speaker is the Same Sky CLS0361-L152 (36 mm, 8 Ω, 2 W, 6 mm deep), not the Visaton K 36 WP. | 2026-09-02.
